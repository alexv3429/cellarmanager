# API reference

The full interactive reference (request/response schemas, try-it-out) is
auto-generated by FastAPI once the server is running, at:

* Swagger UI: `http://localhost:8000/docs`
* ReDoc: `http://localhost:8000/redoc`
* Raw OpenAPI JSON: `http://localhost:8000/openapi.json`

This page is a quick index so you don't have to start the server just to
see what's available. All endpoints except `/auth/*`, `/health`, and
`/i18n/{locale}` require `Authorization: Bearer <token>`.

## Auth

| Method | Path | Notes |
|---|---|---|
| POST | `/auth/register` | Only works while zero users exist (bootstrap) - see `docs/security.md` |
| POST | `/auth/login` | Returns `{access_token, token_type, locale}` |
| POST | `/auth/users` | Add another user; requires being logged in already |

## Wines (catalog)

| Method | Path | Notes |
|---|---|---|
| GET | `/wines?search=` | List/search the catalog |
| GET | `/wines/{id}` | One wine |
| POST | `/wines` | Create a wine directly (without a CSV) |
| PUT | `/wines/{id}?expected_version=N` | Update; 409 on stale version |
| GET | `/wines/{id}/locations` | Every active holding of this wine (requirement 10.b) |

## Cellars

| Method | Path | Notes |
|---|---|---|
| GET | `/cellars` | List, each with `current_fill` |
| GET | `/cellars/{id}` | One cellar |
| POST | `/cellars` | Create; rejects a duplicate `location_rule` |
| PUT | `/cellars/{id}?expected_version=N` | Update |
| DELETE | `/cellars/{id}` | Rejected (409) while bottles still reference it |

## Holdings (add / move / remove - requirement 5.a-c)

| Method | Path | Notes |
|---|---|---|
| GET | `/holdings?wine_id=&cellar_id=&state=` | Filtered list |
| POST | `/holdings/add` | `{wine_id, cellar_id, location, quantity, price_bought?, acquired_date?, client_op_id?}` |
| POST | `/holdings/move` | `{holding_id, quantity, to_cellar_id, to_location, expected_version?, client_op_id?}` |
| POST | `/holdings/remove` | `{holding_id, quantity, reason, expected_version?, client_op_id?}` - `reason` is one of `gifted, broken, sold, lost, drunk` |

`client_op_id` is optional but is how the frontend's offline queue makes a
retried/replayed request idempotent (see `docs/architecture.md`).

## Import / export (requirements 1, 2, 10.c)

| Method | Path | Notes |
|---|---|---|
| POST | `/import` | multipart file upload (`file`), optional `?default_cellar_id=` |
| POST | `/export` | `{columns: [...], language: "en"\|"fr", cellar_id?}` -> CSV text |

## Insights

| Method | Path | Notes |
|---|---|---|
| GET | `/stats?cellar_id=` | Omit `cellar_id` for `{overall, per_cellar}`; include it for one cellar's `StatsResult` |
| GET | `/moveplan` | Suggested moves (requirement 5.e) |
| POST | `/recommendations` | "What should I open?" (requirement 10.a) |

## Enrichment & photo recognition (requirements 5.f, 5.g, 7)

| Method | Path | Notes |
|---|---|---|
| POST | `/wines/{id}/enrich/drinking-window` | Queries every registered provider and returns a combined best estimate, not one site's answer - see below |
| POST | `/wines/{id}/enrich/market-info` | Same idea, for market value + advice |
| POST | `/wines/{id}/photos` | Register a reference photo for later photo-hash matching |
| POST | `/photos/recognize` | Upload a photo; reads the label via OCR *and* checks it against saved reference photos, and returns matches from either or both |

`enrich/*` responses include an `aggregated` object:
`{drink_after, drink_before | market_value, confidence, sources: [...], source_count, per_source: [...]}` -
`per_source` lists each individual provider's own answer before combining,
so the UI (or you, via `/docs`) can see exactly what was combined and how.
See `docs/roadmap.md` for what "several sources" means today (three
deliberately-disagreeing mock providers demonstrating the aggregation) versus
what you'd wire up for real data.

`/photos/recognize` responses look like:
```json
{
  "ocr_available": true,
  "photo_match_available": true,
  "ocr_text": "CHATEAU MARGAUX\n2018",
  "matches": [
    {"wine_id": "...", "producer": "...", "cuvee": null, "vintage": 2018,
     "confidence": 0.92, "ocr_score": 0.92, "photo_score": null, "matched_via": ["ocr"]}
  ]
}
```
`ocr_available`/`photo_match_available` are `false` (not an error) when
that signal's optional dependency isn't installed on the server - see
`docs/roadmap.md` and `requirements.txt`.

## Errors

Errors are returned as `{"detail": "...", "field": "..."?}` with the status
code matching the problem: `400` validation, `401` not authenticated, `403`
forbidden (e.g. registration closed), `404` not found, `409` conflict
(stale version, duplicate name), `429` too many login attempts.
